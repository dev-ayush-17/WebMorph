# Undying Scraper — v0.3 Changelog

> **Version:** 0.3 — Hardening, Heal-Loop Depth, Dashboard Polish
> **Branch:** `feat/v0.3-hardening-and-polish`
> **Status:** Infra complete — mock-mode demo-ready, target site pending

---

## Why this version exists

v0.1 proved the data contract and pipeline skeleton. v0.2 wired in the real Bright Data CLI so swapping from mock to live is one env-var change. But after v0.2, the heal system was shallow (one attempt, no retry, coarse event data), the pipeline had no structured output, products had no memory of what they looked like last time, and the dashboard couldn't show any of that. v0.3 fixes all of that — without requiring a target site or real Bright Data credentials to see any of it working.

---

## What changed and why

### 1. Richer heal event model (`supabase/schema.sql`)

**Problem:** The v0.1/v0.2 `heal_events` table stored only a timestamp, a description string, and a `resolved` boolean. After running, it was impossible to know: Was this a real heal or just a mock simulation? Was this the first attempt or a retry? How long did the heal take? What class of failure triggered it?

**What changed:**
- Added `attempt_number` — which retry number this event represents (1 = first attempt, 2 = first retry)
- Added `heal_method` — `"simulated"` (mock mode, no real CLI call) or `"real"` (live Bright Data call)
- Added `error_type` — typed classification matching the error hierarchy: `empty_result`, `missing_fields`, `type_mismatch`, `cli_auth`, `collector_gone`, `unknown`
- Added `duration_ms` — wall-clock time for the heal attempt in milliseconds

**Why it matters:** Makes post-run analysis useful. You can query "show me all unresolved real heals that were empty_result type" instead of eyeballing description text.

**Upgrade path:** All changes use `ALTER TABLE ADD COLUMN IF NOT EXISTS` so the file is safe to re-run on an existing DB.

---

### 2. `runs` table (new — `supabase/schema.sql`)

**Problem:** There was no record of individual pipeline runs. The dashboard could show current state but not "how has this been running for the past week?"

**What changed:**
- New `runs` table: one row per execution, with `run_id`, `started_at`, `finished_at`, `status`, and `summary_json`
- `summary_json` is a JSONB column containing the full structured run summary: products found, price/stock change counts, heal event counts, duration
- The pipeline writes a `running` row at start and updates it to `healthy`/`degraded`/`failed` at end — so any crash mid-run is visible as a stuck `running` row

---

### 3. Retry + backoff (`src/retry.js`)

**Problem:** v0.2's live-mode heal attempt happened once. If it failed due to a transient network error, the event was logged as unresolved with no retry. Real scrapers need at least one retry to distinguish "broken site" from "blip."

**What changed:**
- New `src/retry.js` — a clean `withRetry(fn, options)` wrapper with linear backoff (delay = `BASE_DELAY_MS × attempt`)
- Default: 2 total attempts (configurable via `maxRetries`)
- `noDelay` option for instant execution in unit tests
- `onRetry` callback for per-attempt logging
- `heal-check.js` uses `withRetry()` for the real-heal path — mock path is untouched

**Why 2 attempts, not 3 or 5:** Hackathon scope. Two attempts catches transient failures without burning Bright Data quota or delaying the pipeline by minutes. Easy to increase via the `MAX_RETRIES` constant.

---

### 4. Price change detection (`src/diff.js`)

**Problem:** Every pipeline run wrote products as if seeing them for the first time. You couldn't tell whether a price went up, down, or stayed the same since the last run. For a price tracker, this is the core value proposition.

**What changed:**
- New `src/diff.js` with two exports: `diffProducts()` and `buildDiffSummary()`
- `diffProducts()` takes new products + a `Map<url, {price, in_stock}>` of prior snapshots, and returns each product enriched with `price_changed`, `stock_changed`, `previous_price`
- Change threshold: `$0.01` — avoids false positives from floating-point representation noise in mock data
- The pipeline fetches prior snapshots via a Supabase query before writing, then passes them through `diffProducts()`
- In dry-run mode (no Supabase), no prior snapshots exist → all products are "new" → safe graceful degradation

**Schema impact:** `products` table now has `price_changed`, `stock_changed`, `previous_price` columns (added via `ALTER TABLE IF NOT EXISTS`).

---

### 5. Structured pipeline run summary (`scripts/run-pipeline.js`)

**Problem:** The pipeline printed a simple summary box but the information wasn't persisted or machine-readable. Post-run analysis required reading log files.

**What changed:**
- `openRunRecord()` / `closeRun()` write to the new `runs` table
- A structured `runSummary` object is built at the end of each run and stored as `summary_json`
- The console summary is richer: shows `↑N price↑  ↓N price↓`, stock flips, heal events resolved/unresolved
- All Supabase calls degrade gracefully: `openRunRecord()` and `fetchPriorSnapshots()` are non-fatal — a DB failure doesn't crash the pipeline, it logs a warning and continues

---

### 6. Error handling audit (cross-cutting)

**Problem:** v0.1/v0.2 had some Supabase calls that would throw and crash the pipeline if the DB was unreachable or misconfigured.

**What changed:**
- `openRunRecord()`: failure is `console.warn` only — non-fatal
- `fetchPriorSnapshots()`: failure returns empty Map — non-fatal
- `writeHealEvents()` / `writeProducts()`: still throw (intentional — these are the primary outputs, failure should surface)
- Discord: already non-fatal since v0.1 — confirmed unchanged
- Bright Data CLI wrapper: already uses typed errors — confirmed unchanged

---

### 7. Dashboard polish (`dashboard/`)

**Problem:** The dashboard showed a snapshot of current state with no context about what changed. The health timeline showed only resolution status with no detail.

**What changed:**

**ProductTable (v0.3):**
- ▲/▼ price delta chip with previous price in tooltip (color-coded: red for increases, green for decreases)
- "flipped" badge on stock column when `stock_changed = true`
- "new" amber badge on product name when `previous_price = null` (first-seen product)
- Subtle amber row highlight for any changed product
- Change summary bar above the table: "⚡ N products changed since last run"

**HealthTimeline (v0.3):**
- Three visually distinct card states: resolved (green), unresolved (red), simulated (amber)
- Chip row below each event description: error type, heal method, attempt number, duration
- Error type and method chips are color-coded to match their severity

**RunHistory (new in v0.3):**
- Table of recent pipeline runs from the `runs` table
- Columns: run ID, status badge, products found, price changes, stock flips, heal event ratio (resolved/total), duration, start time
- Status badges: ✓ Healthy (green), ⚠ Degraded (amber), ✗ Failed (red), ⟳ Running (blue)
- Rows subtly tinted per status

---

### 8. Test suite (`tests/pipeline-integration.test.js`)

**Problem:** There were 20 unit tests for the Bright Data CLI wrapper and registry, but no coverage for the diff module, retry logic, or end-to-end mock pipeline behavior.

**What changed:** 21 new tests across 6 categories:
- `diffProducts` — 6 cases: new products, price up/down, noise threshold, stock flip, unchanged stock
- `buildDiffSummary` — 1 case: correct counts for mixed input
- `withRetry` — 4 cases: success first attempt, success on retry, exhaustion, onRetry callback
- `checkResult` mock mode — 5 cases: valid, empty, non-array, field validation, partial valid
- `checkResult` live mode (injected) — 3 cases: heal succeeds, heal exhausted, heal OK but retry fails
- Full pipeline smoke test — 2 cases: zero env vars, mock round-trip

All 21 pass. No real credentials or CLI needed.
